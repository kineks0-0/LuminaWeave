# 插件注入提示词的不同路径思考

在 SillyTavern (ST) 的架构下，实现**“插件专属提示词”**或**“背景强约束”**的注入有多条技术路径。以下列出从 ST 内部扩展机制到全面旁路接管的至少 10 种注入方案。

**排序标准：**
- **侵入度（低 -> 高）**：改变 ST 既有核心逻辑的程度（越低代表越不修改 ST 原生状态与源码）。
- **兼容性（高 -> 低）**：在 ST 更新版本后的存活概率，以及与其他插件的兼容难易。

---

## 路线维度一：受限的官方机制（低侵入，高兼容）

### 1. 官方扩展 API 注入 (Extension Prompt / Author's Note API)
* **侵入度：★☆☆☆☆ | 兼容性：★★★★★**
* **原理**：调用 ST 原生的扩展注册接口（如 `extension_prompt`），或者直接读写 `chat_metadata` 以触发官方的 Author's Note（作者的话）和 Memory（记忆模块）。
* **优点**：此乃官方钦定途径，API 最稳定，能在第一时间兼容 ST 的系统更新。
* **缺点**：注入位置极其受限（通常只能控制在 `depth` 偏移或特定位置），无法做拆分到 System Prompt 最顶层或最末端的精细化构建。

### 2. 自定义预设宏替换 (Preset Marker Replacement)
* **侵入度：★☆☆☆☆ | 兼容性：★★★★★**
* **原理**：要求用户配合，在 ST 的“系统预设 (Context Preset)”中手动插入自定义的占位符（如 `{{lumina_inject_here}}`）。插件在生成周期内向系统注册该宏的解析回调，或在发信前进行纯文本替换。
* **优点**：给予了玩家极大的自由度，玩家想把插件逻辑放在结构图里的哪里都可以。
* **缺点**：强烈依赖用户的设置正确性。如果玩家切换了一个没有该宏的预设，插件所有的请求控制指令就会意外丢失。

### 3. 用户输入预处理拦截 (Input Interceptor / Chat Modifier)
* **侵入度：★★☆☆☆ | 兼容性：★★★★☆**
* **原理**：在用户点击“发送消息”或触发 `Generate()` 之前，立即劫持内容流。例如将原始输入 `[用户说了你好]` 隐式替换为 `[用户说了你好] \n (系统规则：请检查物品栏)`。
* **优点**：技术难度小，逻辑独立，绝不会破坏前置的历史记录。
* **缺点**：指令总是作为新的一条发言紧贴在用户话语末尾，无法作为全局 System Rule 前置，甚至可能因为上下文滑动被模型忽视其作为“强制规则”的权重。

### 4. 虚拟历史消息伪装 (Virtual History Forgery)
* **侵入度：★★☆☆☆ | 兼容性：★★★★☆**
* **原理**：在内存层面临时修饰 `window.chat` 或 `context` 数组。在将其投喂给 Prompt 构建器前，伪造一条并不展示在 UI 中的 `System` 或 `Assistant` 消息，诱导大模型行为。完成后将假消息隐式截断。
* **优点**：能原生利用“多轮对话历史”这一具有高关注度和自然对话权重的下端区域。
* **缺点**：可能扰乱 ST 内部复杂的 Token 裁剪预算（Budgeting）机制，若把握不好尺寸容易导致正当历史被意外挤掉截断。

## 路线维度二：中间件与网络层拦截（中等侵入，独立网关）

### 5. API 中间件反代服务 (Local API Proxy)
* **侵入度：★★★☆☆ | 兼容性：★★★★☆**
* **原理**：让用户将 ST 配置的 API Base URL 设置为插件本地拉起的代理网址（如 `http://localhost:3000/proxy`）。ST 发出组装好的标准 JSON 给代理，代理服务拆包插入插件提示词后，再转发给真正的 OpenAI 等接口。
* **优点**：插件与 ST 前端重构风险完全隔离。只认标准网络协议流，无视 ST 的内部变化变动。
* **缺点**：破坏了原有直连的开箱即用性并引入代理开销；同时丢失了语义上下文（难以区分发来的一整条 Payload 中哪些是设定、哪些是单纯记录代码块，导致插入位置不够精准）。

### 6. 前端网络底层劫持 (XHR / Fetch Monkey Patch)
* **侵入度：★★★☆☆ | 兼容性：★★★☆☆**
* **原理**：前端层面的网络拦截。注入脚本修改浏览器的原生 `window.fetch` 或 `XMLHttpRequest`。当发现目的是特定的生成请求时，临时拦截并在网络底层覆写 Body payload 中的 `messages` 数组以嵌插内容。
* **优点**：无需配置外部代理解决跨域限制，能自动起效在发出请求离线的最后一刻卡住并加塞内容。
* **缺点**：Hook 可能会引发不可预期的冲突竞争异常（例如部分需要抓包分析的第三方网络嗅探插件）。

### 7. API 分发适配器覆盖 (Override ST API Adapters)
* **侵入度：★★★☆☆ | 兼容性：★★★☆☆**
* **原理**：动态定位 ST 本地不同的特定 API 适配器（例如引用的 `public/scripts/openai.js` `prepareOpenAIMessages` 等）。将自身封装后的生成函数进行函数出口前劫持以注入插件词条。
* **优点**：在这个阶段拦截时获得的提示词结构化数组最为完整并清晰，能够精确定向覆盖。
* **缺点**：ST 兼容几十个如 Kobold, Claude 等截然不同结构的模型接口组装规范。如果要支持全覆盖，每个接口适配器均需要编写一份特定的注入补丁代码。

## 路线维度三：系统核心拦截与接管（强侵入级，深度介入）

### 8. 抽象组装管线篡改 (Monkey Patch `PromptManager`)
* **侵入度：★★★★☆ | 兼容性：★★☆☆☆**
* **原理**：针对 ST 组装所有碎片的“腹地”。拦截 `PromptManager.preparePrompt` 钩子闭包。在此阶段将需要的核心约束（如 Lumina 的 Pre-Context 等规则插槽）先期排队混流插入 `PromptCollection` 组装序列中。
* **优点**：能够取得最高决策优先级的结构操控权，可以控制 System 区块或者插入新角色而完美服从后续流程。
* **缺点**：深度依赖 ST 当前的 `PromptManager` 数据结构方法树签名。一旦 ST 官方对组装管线进行重命名或重构，该方案完全失效。

### 9. 底层引擎接管机制 (Override `substituteParams` Core)
* **侵入度：★★★★★ | 兼容性：★☆☆☆☆**
* **原理**：把 ST 应用最底层的文本全局替换和宏解析计算引擎替换装载自己的定制版本。这使得在整个 ST 发信的字句计算流转期里，任何一行处理过的字符串都会首先执行指定的强行注入回调代码链逻辑。
* **优点**：注入粒度可缩小至“字串中包含条件词元即自动强行附加段落触发逻辑”等极端精微操控。
* **缺点**：不仅是在发信中，大量的卡片显示重载或者系统环境的加载都容易调用引擎底层计算钩子。过载的劫持直接导致全系统层面阻塞并诱发致命的内存堆栈崩溃泄漏风险。

### 10. 完全旁路构建重构与发送 (Independent ST-Bypass Builder Process)
* **侵入度：★★★★★ (全局自定重组) | 兼容性：☆☆☆☆☆ (完全脱离 ST 管控架构)**
* **原理**：即“完全自己复现并构建一切发信”。插件利用 ST 端仅作为一数据供给库：它抽取 ST 的所有角色、设置、世界书设定乃至所有的历史文本记忆池；随后自主利用如独立的 PromptBuilder 体系和重现打片截断裁剪器（Context/Token Budgeting），独自拼凑完整的交互载荷通过自带发送模块 `generateCustomStream()` 自发信请求。完成回转流后再原路手动硬塞入回 ST 系统并迫使其刷新。
* **优点**：自由无上限边界设计。它使得例如 LuminaWeave V5.3 构想中支持异构发散型推演计划树（Piggyback/Async 复合策略）和分层重构彻底化摆脱束缚等一切复杂方案得以最高保真复现与精准调度。
* **缺点**：插件负担完全接演所有发信组件计算任务。倘若后期 ST 追加了重要底层交互（语音支持识别逻辑改变或者多维模型视觉多模态能力新解析破窗注入规则框架等改动），完全重制剥离的侧载系统意味着全套复现成本和彻底无兼容升级可能。
